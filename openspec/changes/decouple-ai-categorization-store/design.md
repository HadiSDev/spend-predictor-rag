## Context

The sync pipeline's keyword categorizer (`ai_api/sync/categorizer.py`, a stand-in
for the Qdrant/LLM categorizer) writes its output — predicted category, a
`level_1/2/3` + `account_code`/`account_name` snapshot, `confidence`, `rationale`
— plus synthetic `gt_*` ground truth onto columns of the `web_api` domain model
`InvoiceLine`. `_build_summary` then rolls spend up by `InvoiceLine.level_2`.

This couples the business domain to the AI pipeline's working data and violates
the project's one-way boundary (`ai_api` imports `web_api`, never the reverse):
the domain table carries fields only the AI workflow touches. All persistence
today lives in `web_api` (SQLModel models + a single Alembic chain under
`web_api/db/migrations`); `ai_api` owns **no** tables.

A prior step added `InvoiceLine.spend_category_id` (schema-only FK, not yet
populated) as the domain-level line→category assignment. That column stays.

## Goals / Non-Goals

**Goals:**
- Remove AI-produced columns (`level_1/2/3`, `account_code`, `account_name`,
  `confidence`, `rationale`, `gt_level_1/2/3`, `gt_account_code`) and `line_erp_id`
  from `InvoiceLine`.
- Give `ai_api` its own persistence for categorization results, referencing domain
  rows by id, with no ORM coupling back into the domain.
- Keep the sync pipeline fully functional: the spend rollup still works, and
  synthetic ground truth is still recorded for benchmarking.
- Preserve `web_api` ↛ `ai_api`: `web_api` never imports the AI store.

**Non-Goals:**
- Wiring `spend_category_id` population against seeded `SpendCategory` rows —
  still deferred (that FK stays nullable/unpopulated for now).
- Adding a `gt_spend_category_id` FK.
- Standing up a separate database or a second Alembic environment for `ai_api`.
- Changing the categorizer's matching algorithm.

## Decisions

### 1. AI results live in a new `ai_api`-owned table in the same Postgres
A new `LineCategorization` SQLModel is defined under `src/ai_api/persistence/`
(new module) and holds: `invoice_line_id`, `spend_category_id` (nullable),
predicted `level_1/2/3` + `account_code`/`account_name` snapshot, `confidence`,
`rationale`, and the `gt_level_1/2/3` + `gt_account_code` ground truth. One row per
categorized line (unique on `invoice_line_id`).

*Why:* the runner already uses `web_api.db.session.engine`; a single DB keeps the
sync one transaction and avoids premature infra. *Alternative — separate DB:*
rejected as unjustified for a benchmark-stage pipeline.

### 2. Reference domain rows by id; no ORM relationship into the domain
`invoice_line_id` and `spend_category_id` are FK **columns** (DB-level, direction
`ai_api → web_api`, `ON DELETE CASCADE` on the line) but there is **no** SQLModel
`Relationship()` into domain classes and **no** back-population on `InvoiceLine`.
`web_api` models never import or mention `LineCategorization`.

*Why:* DB FKs give referential integrity and cascade cleanup while the absence of
ORM relationships keeps the Python-level dependency strictly one-way. *Alternative
— plain id columns with no FK:* looser integrity, orphan rows on line delete;
rejected.

### 3. Migration ownership stays with the single existing Alembic chain
The one Alembic chain under `web_api/db/migrations` migrates the whole database,
including the new AI table. Migrations here are **hand-authored** (0001–0009),
never autogenerated.

*Why:* the AI table FK-references `invoice_lines` in the same chain, so ordering
is trivial; a second Alembic env would add real overhead and cross-chain ordering
fragility. Ownership is expressed in **code** (the model + all queries live in
`ai_api`), not in which folder the DDL script sits. *Revisit* only if `ai_api`
ever needs an independent database.

### 4. The spend rollup reads the AI store, not the domain line
`_build_summary` (already `ai_api` code) rolls spend up by the **predicted
`level_2` in `LineCategorization`**, joined to `InvoiceLine` for the amount. This
keeps a meaningful rollup without domain columns and without needing seeded
`SpendCategory`.

*Why:* moves the read to where the data now lives (ai_api), so removing the domain
columns doesn't degrade the pipeline. *Alternative — roll up via
`spend_category_id`:* it's null until seeding lands, so the rollup would be empty;
rejected for now.

### 5. The runner writes the AI store; sets `spend_category_id` only when resolvable
`_categorize_pending` upserts a `LineCategorization` row per line (prediction +
evidence + ground truth) and sets `InvoiceLine.spend_category_id` only if the
match resolves to a real `SpendCategory` (still null until seeding). Line/invoice
`status` transitions stay on the domain model (domain lifecycle, not AI evidence).

## Risks / Trade-offs

- **Shared `SQLModel.metadata` could let autogenerate propose dropping the AI
  table** → migrations are hand-written (autogenerate isn't used), and the Alembic
  env's `target_metadata` will import the AI model so metadata stays complete;
  `create_all` in tests also sees it.
- **`create_all` must register the AI model before use** → the runner imports
  `ai_api.persistence`, so any path that runs the sync (and the test fixtures that
  import the runner) registers the table.
- **DB FK `ai_api → web_api` creates a deploy-ordering dependency** → mitigated by
  the single migration chain (Decision 3).
- **Dropping columns loses existing categorization data** → acceptable
  pre-production (synthetic/benchmark data; the pipeline is reset-friendly). No
  backfill.

## Migration Plan

1. Add migration `0010`: create `line_categorizations` (AI store) and drop the
   removed columns from `invoice_lines`. Reversible (downgrade re-adds the columns
   and drops the table).
2. Apply against the live DB on port 5433.
3. Rollback: `alembic downgrade -1` restores the columns and drops the AI table;
   no data preservation guarantees for the dropped columns (pre-production).

## Open Questions

- None blocking. Long-term, whether the ground-truth snapshot should reference a
  `SpendCategory` id rather than denormalized `gt_level_*` is deferred with the
  broader "wire the categorizer to a seeded spend tree" work.
